# 架构演进与最佳实践

## 从贫血模型到充血模型

### 贫血模型（Anemic Domain Model）

贫血模型是指领域对象只包含数据（字段和getter/setter），不包含业务逻辑，业务逻辑分散在服务层。

```java
// 贫血模型示例
@Entity
public class Loan {
    private LoanId loanId;
    private CopyId copyId;
    private UserId userId;
    private LocalDateTime createdAt;
    private LocalDate expectedReturnDate;
    private LocalDateTime returnedAt;

    // 只有getter和setter，没有业务逻辑
    public LoanId getLoanId() { return loanId; }
    public void setLoanId(LoanId loanId) { this.loanId = loanId; }

    public LocalDateTime getReturnedAt() { return returnedAt; }
    public void setReturnedAt(LocalDateTime returnedAt) { this.returnedAt = returnedAt; }
}

// 业务逻辑在服务层
@Service
public class LoanService {
    public void createLoan(CopyId copyId, UserId userId) {
        // 业务逻辑分散在服务层
        if (!loanRepository.isAvailable(copyId)) {
            throw new IllegalStateException("Copy not available");
        }

        Loan loan = new Loan();
        loan.setLoanId(new LoanId());
        loan.setCopyId(copyId);
        loan.setUserId(userId);
        loan.setCreatedAt(LocalDateTime.now());
        loan.setExpectedReturnDate(LocalDate.now().plusDays(30));

        loanRepository.save(loan);
    }

    public void returnLoan(LoanId loanId) {
        Loan loan = loanRepository.findById(loanId).orElseThrow();

        // 业务逻辑在服务层
        LocalDateTime now = LocalDateTime.now();
        loan.setReturnedAt(now);

        if (now.isAfter(loan.getExpectedReturnDate().atStartOfDay())) {
            // 计算逾期费用
            calculateLateFee(loan);
        }

        loanRepository.save(loan);
    }
}
```

**贫血模型的问题：**
1. 业务逻辑分散，难以维护
2. 领域对象只是数据容器，没有表达业务含义
3. 违反面向对象设计原则
4. 容易产生重复的业务逻辑

### 充血模型（Rich Domain Model）

充血模型是指领域对象包含数据和业务逻辑，业务逻辑封装在领域对象内部。

```java
// 充血模型示例（本项目实现）
@Entity
public class Loan extends AbstractAggregateRoot<Loan> {
    @EmbeddedId
    private LoanId loanId;
    @Embedded
    @AttributeOverride(name = "id", column = @Column(name = "copy_id"))
    private CopyId copyId;
    @Embedded
    @AttributeOverride(name = "id", column = @Column(name = "user_id"))
    private UserId userId;
    private LocalDateTime createdAt;
    private LocalDate expectedReturnDate;
    private LocalDateTime returnedAt;

    @Version
    private Long version;

    // 业务逻辑在构造函数中
    public Loan(CopyId copyId, UserId userId, LoanRepository loanRepository) {
        Assert.notNull(copyId, "copyId must not be null");
        Assert.notNull(userId, "userId must not be null");
        Assert.isTrue(loanRepository.isAvailable(copyId),
            "copy with id = " + copyId + " is not available");

        this.loanId = new LoanId();
        this.copyId = copyId;
        this.userId = userId;
        this.createdAt = LocalDateTime.now();
        this.expectedReturnDate = LocalDate.now().plusDays(30);

        this.registerEvent(new LoanCreated(this.copyId));
    }

    // 业务逻辑在方法中
    public void returned() {
        this.returnedAt = LocalDateTime.now();

        if (this.returnedAt.isAfter(expectedReturnDate.atStartOfDay())) {
            // 计算逾期费用
            calculateLateFee();
        }

        this.registerEvent(new LoanClosed(this.copyId));
    }

    private void calculateLateFee() {
        // 逾期费用计算逻辑
    }
}

// 服务层只负责编排
@UseCase
public class RentBookUseCase {
    public void execute(CopyId copyId, UserId userId) {
        // 只负责编排，不包含业务逻辑
        loanRepository.save(new Loan(copyId, userId, loanRepository));
    }
}
```

**充血模型的优势：**
1. 业务逻辑集中，易于维护
2. 领域对象具有业务含义
3. 符合面向对象设计原则
3. 减少重复逻辑

## 事务边界管理

### 事务边界原则

在DDD中，一个聚合根对应一个事务边界。

```java
// 正确：一个事务操作一个聚合
@UseCase
@Transactional
public class RentBookUseCase {
    public void execute(CopyId copyId, UserId userId) {
        // 只操作Loan聚合
        Loan loan = new Loan(copyId, userId, loanRepository);
        loanRepository.save(loan);

        // Copy聚合通过事件异步更新
    }
}

// 错误：一个事务操作多个聚合
@UseCase
@Transactional
public class RentBookUseCase {
    public void execute(CopyId copyId, UserId userId) {
        // 操作Loan聚合
        Loan loan = new Loan(copyId, userId, loanRepository);
        loanRepository.save(loan);

        // 直接操作Copy聚合（不应该这样做）
        Copy copy = copyRepository.findById(copyId).orElseThrow();
        copy.makeUnavailable();
        copyRepository.save(copy);
    }
}
```

### 事务传播策略

```java
@Service
public class BookService {

    @Transactional(propagation = Propagation.REQUIRED)
    public void addBookWithCopies(BookDto bookDto, int copyCount) {
        // REQUIRED：如果没有事务则创建新事务，如果有则加入现有事务
        Book book = createBook(bookDto);
        bookRepository.save(book);

        for (int i = 0; i < copyCount; i++) {
            createCopy(book.getId());
        }
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logBookAddition(BookId bookId) {
        // REQUIRES_NEW：总是创建新事务
        auditService.log("Book added: " + bookId);
    }

    @Transactional(propagation = Propagation.MANDATORY)
    public void updateBookMetadata(BookId bookId, String metadata) {
        // MANDATORY：必须在现有事务中执行
        book.getMetadata().update(metadata);
        bookRepository.save(book);
    }
}
```

### 事务隔离级别

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
public void updateBook(BookId bookId, String title) {
    // READ_COMMITTED：防止脏读
    Book book = bookRepository.findById(bookId).orElseThrow();
    book.setTitle(title);
    bookRepository.save(book);
}

@Transactional(isolation = Isolation.REPEATABLE_READ)
public void getBookStatistics(BookId bookId) {
    // REPEATABLE_READ：防止脏读和不可重复读
    return bookRepository.findStatistics(bookId);
}
```

## 性能考虑

### 1. 聚合设计原则


### 2. 懒加载策略

```java
@Entity
public class Book {
    @EmbeddedId
    private BookId id;
    private String title;

    @OneToMany(fetch = FetchType.LAZY, mappedBy = "book")
    private List<Copy> copies;  // 懒加载
}

// 使用时需要确保事务开启
@Transactional
public BookDto getBookWithCopies(BookId bookId) {
    Book book = bookRepository.findById(bookId).orElseThrow();
    // 触发懒加载
    List<Copy> copies = book.getCopies();
    return new BookDto(book, copies);
}
```

### 3. 批量操作

```java
public interface BookRepository extends CrudRepository<Book, BookId> {

    // 使用原生SQL进行批量操作
    @Modifying
    @Query("UPDATE Book b SET b.title = :title WHERE b.id IN :ids")
    int updateTitles(@Param("title") String title, @Param("ids") List<BookId> ids);

    // 批量保存
    default List<Book> saveAll(List<Book> books) {
        List<Book> savedBooks = new ArrayList<>();
        for (Book book : books) {
            savedBooks.add(save(book));
        }
        return savedBooks;
    }
}
```

## 扩展性设计

### 1. 策略模式

```java
// 定义费用计算策略
public interface LateFeeCalculator {
    Money calculate(Loan loan);
}

// 普通用户费用计算
@Component
public class RegularUserFeeCalculator implements LateFeeCalculator {
    @Override
    public Money calculate(Loan loan) {
        long daysOverdue = ChronoUnit.DAYS.between(
            loan.getExpectedReturnDate(),
            loan.getReturnedAt().toLocalDate()
        );
        return Money.of(daysOverdue * 0.50);  // 每天0.5元
    }
}

// VIP用户费用计算
@Component
public class VipUserFeeCalculator implements LateFeeCalculator {
    @Override
    public Money calculate(Loan loan) {
        long daysOverdue = ChronoUnit.DAYS.between(
            loan.getExpectedReturnDate(),
            loan.getReturnedAt().toLocalDate()
        );
        return Money.of(daysOverdue * 0.25);  // 每天0.25元
    }
}

// 使用策略
@Service
public class LoanService {
    private final Map<UserType, LateFeeCalculator> calculators;

    public LoanService(List<LateFeeCalculator> calculators) {
        this.calculators = calculators.stream()
            .collect(Collectors.toMap(
                this::getUserTypeForCalculator,
                Function.identity()
            ));
    }

    public Money calculateLateFee(Loan loan, UserType userType) {
        return calculators.get(userType).calculate(loan);
    }
}
```

### 3. 事件溯源扩展

```java
// 事件存储接口
public interface EventStore {
    void save(LoanId aggregateId, List<DomainEvent> events);
    List<DomainEvent> getEvents(LoanId aggregateId);
}

// 事件存储实现
@Service
public class JpaEventStore implements EventStore {
    private final EventRecordRepository eventRecordRepository;

    @Override
    @Transactional
    public void save(LoanId aggregateId, List<DomainEvent> events) {
        for (DomainEvent event : events) {
            EventRecord record = new EventRecord(
                aggregateId,
                event.getClass().getSimpleName(),
                serializeEvent(event),
                LocalDateTime.now()
            );
            eventRecordRepository.save(record);
        }
    }

    @Override
    public List<DomainEvent> getEvents(LoanId aggregateId) {
        return eventRecordRepository.findByAggregateId(aggregateId).stream()
            .map(this::deserializeEvent)
            .toList();
    }
}

// 聚合重建器
@Service
public class LoanRebuilder {
    private final EventStore eventStore;

    public Loan rebuild(LoanId loanId) {
        List<DomainEvent> events = eventStore.getEvents(loanId);
        Loan loan = null;

        for (DomainEvent event : events) {
            if (event instanceof LoanCreated created) {
                loan = new Loan(created.copyId(), created.userId(), null);
            } else if (event instanceof LoanClosed && loan != null) {
                loan.returned();
            }
        }

        return loan;
    }
}
```

## 最佳实践总结

### 1. 领域建模

- **使用充血模型**：将业务逻辑封装在领域对象中
- **小聚合原则**：保持聚合小而专注
- **值对象不可变**：使用Java record实现不可变性
- **类型安全**：使用强类型ID而不是String或Long

### 2. 架构设计

- **清晰的限界上下文**：明确模块边界
- **依赖倒置**：高层模块不依赖低层模块
- **接口隔离**：通过接口隔离具体实现
- **事件驱动**：使用领域事件实现松耦合

### 3. 代码质量

- **命名规范**：使用业务术语命名
- **单一职责**：每个类只有一个改变的理由
- **开闭原则**：对扩展开放，对修改关闭
- **代码注释**：解释"为什么"而不是"是什么"

### 4. 性能优化

- **合理使用缓存**：减少数据库访问
- **避免N+1查询**：使用JOIN FETCH
- **批量操作**：减少数据库往返
- **懒加载**：按需加载数据

### 5. 可测试性

- **依赖注入**：便于测试时替换依赖
- **接口抽象**：便于Mock实现
- **测试隔离**：每个测试独立运行
- **覆盖率目标**：设定合理的覆盖率

### 6. 可维护性

- **代码组织**：按功能而非技术分层
- **文档完善**：保持文档与代码同步
- **重构勇气**：持续改进代码质量
- **代码审查**：确保代码质量

## 项目总结

这个图书馆管理项目虽然是简单的示例，但它完整展示了DDD的核心概念在Spring框架中的实现：

1. **战略设计**：清晰的限界上下文划分
2. **战术设计**：聚合、实体、值对象的正确使用
3. **领域事件**：实现跨上下文的松耦合通信
4. **仓储模式**：抽象持久化细节
5. **应用服务**：用例编排和事务管理
6. **基础设施**：技术关注点隔离
7. **Spring集成**：充分利用Spring框架特性
8. **测试策略**：完整的测试体系

通过学习这个项目，可以理解如何在实践中应用DDD，构建出清晰、可维护、可扩展的企业级应用。
